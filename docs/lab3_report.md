# Лабораторная работа №3. Метрики программного кода

**Дисциплина:** Технологии разработки программного обеспечения
**Проект:** Investment Assistant — Telegram-бот, инвестиционный ассистент на T-Invest MCP (Python 3.12)
**Репозиторий:** https://github.com/Rudimix/InvestmentAssistant, ветка `feature/assistant-and-lab3-metrics`

## 1. Задание

1. Построить не менее 5 метрик программного кода.
2. Проанализировать результаты.
3. Оптимизировать код на основе метрик.
4. Перестроить метрики для улучшенного кода.
5. Сделать выводы.

В методичке метрики строятся средствами Visual Studio для C# (меню «Анализ → Метрики кода»,
`msbuild /t:Metrics`, правила CA1501/CA1502/CA1505/CA1506). Проект написан на Python, поэтому
используются готовые инструменты анализа Python-кода, которые считают те же метрики.

## 2. Объект измерения

Пакет `src/investment_journal` (12 модулей, около 1200 строк):

## 3. Инструменты

| Метрика Visual Studio | Инструмент Python | Команда | Комментарий |
|---|---|---|---|
| Maintainability Index | **radon** | `radon mi -s` | Шкала 0–100. Ранги A (> 19), B (10–19), C (< 10) совпадают с зелёной, жёлтой и красной зонами VS. Считается для модуля целиком |
| Cyclomatic Complexity | **radon** | `radon cc -s -a` | По функциям и методам, ранги A–F. Для перекрёстной проверки — **lizard** (CCN) и **pyscn** |
| Правило CA1502 (CC > N) | **flake8 + mccabe** | `flake8 --select C901` | Порог `max-complexity = 10` в `.flake8`, как в примере методички. Дополнительно `lizard -C 10 -w` |
| Class Coupling | **pyscn** | `pyscn analyze --json` | CBO (Coupling Between Objects) по классам. Связи модулей: Ca, Ce и нестабильность I = Ce / (Ca + Ce) |
| Depth of Inheritance | **pylint** | `pylint --enable=too-many-ancestors --max-parents=0` | R0901 выводит число предков для каждого класса. pylint не считает `object`, поэтому DIT VS = значение pylint + 1 |
| Правила CA15xx | **pylint** (design checker) | `pylint --enable=design` | Пороги в `[tool.pylint.design]` в `pyproject.toml`: `max-parents = 5` (≈ CA1501), `max-branches`, `max-locals` и др. |
| Source Lines / Executable Lines | **radon** | `radon raw -s` | LOC — все строки, LLOC — логические строки (операторы), SLOC, комментарии, пустые |
| — | **radon** | `radon hal` | Метрики Холстеда: объём V, сложность, оценка числа ошибок B |
| — | **pyscn** | `pyscn analyze` | Когнитивная сложность, LCOM4, дублирование кода, мёртвый код, итоговая оценка health score |
| — | **coverage.py** | `coverage run -m unittest` | Покрытие операторов и ветвей тестами |

Все команды собраны в `scripts/metrics.ps1`. Скрипт только запускает инструменты и сохраняет их
вывод без изменений:

```powershell
python -m pip install -e ".[metrics]"
.\scripts\metrics.ps1 -Out metrics\after
```

Отчёты: `metrics/before/` (до оптимизации) и `metrics/after/` (после). HTML-отчёт pyscn —
`pyscn.html` в каждом каталоге.

Замер «до» снят с коммита `f91db41` (первая версия), замер «после» — с итогового коммита ветки.

## 5. Анализ результатов

1. **В целом код сопровождаемый.** Все модули имеют ранг A по MI (radon), дублирования и мёртвого
   кода нет, LCOM4 = 1 у всех классов: каждый класс — одна связная группа методов. Проблемы
   сосредоточены в шести методах с CC > 10.
2. **`MarketDataService.portfolio` — главная точка риска.** Это единственный метод с рангом D
   (CC 30) и максимальной когнитивной сложностью (38). Метод четыре раза повторяет одно и то же
   ветвление «словарь `{units, nano}` или число». Высокое значение подтверждает и метрика
   Холстеда: у `market` объём 705 и оценка ошибок 0,235 при всего 96 строках, это второе место
   в пакете. Модуль `market` имеет и один из худших MI — 35,19.
3. **`analytics`** — максимальный объём Холстеда (819). В `review_decision` три почти одинаковые
   ветки buy/sell/hold с вложенными `if` (когнитивная сложность 35, pylint R0912 — 16 ветвей).
   `candle_stats` смешивает пять расчётов в одном теле (CC 18, R0914 — 16 локальных переменных,
   R1731 — ручная реализация `max`).
4. **`InvestmentAgent.ask`** имеет наибольшую вложенность (4). Он совмещает цикл диалога, разбор
   аргументов от LLM, маршрутизацию по инструментам и обработку ошибок. pylint W0212 указывает на
   обращение к закрытому полю чужого объекта (`journal.market._tools`) — скрытую связь в обход
   публичного интерфейса.
5. **`parse_tool_result`, `load_settings`, `cmd_stats`** — сложность на границе порога из-за
   длинных цепочек проверок.
6. **Инструменты по-разному считают цикломатическую сложность.** У `portfolio` radon и lizard дают
   30, а mccabe (flake8) и pyscn — 8: первые две считают каждое `or`/`and` отдельной ветвью
   (`x.get("units", 0) or 0`), вторые — нет. Поэтому flake8 этот метод не пометил. Когнитивная
   сложность (pyscn, 38) подтверждает, что метод действительно трудно читать.
7. **Связанность и наследование в норме.** Максимальный CBO — 4 (`MarketDataService`,
   `JournalRepository`). Наибольшая эфферентная связанность у слоёв-«склеек» `bot` и `__main__`
   (Ce = 7, I ≈ 0,9–1), что ожидаемо для внешнего слоя. Самые устойчивые модули — `models` и
   `config` (I = 0): от них зависят, сами они ни от чего не зависят. Циклических зависимостей нет.
   Глубина наследования 3 (по pylint) есть только у исключений (`ToolError → RuntimeError →
   Exception → BaseException`), правило `max-parents = 5` не нарушено.
8. **Покрытие тестами — 95 %.** Модуль `__main__` не покрыт (0 %), потому что сборка приложения
   смешана с запуском polling.

## 6. Оптимизация кода на основе метрик

## 8. Выводы

1. Для Python построены все метрики из методички: индекс сопровождаемости (radon), цикломатическая
   сложность (radon, lizard, mccabe, pyscn), связанность классов CBO (pyscn), глубина наследования
   (pylint), строки исходного и исполняемого кода (radon raw). Дополнительно сняты метрики Холстеда,
   когнитивная сложность, LCOM4, связанность модулей Ca/Ce/I, дублирование и покрытие тестами.
   Аналогом правил CA1501/CA1502 служат flake8 C901 и проверки дизайна pylint с порогами в
   `.flake8` и `pyproject.toml`.
2. Метрики точно указали проблемные места. Шесть методов с CC > 10 при разборе оказались либо
   дублированием (`portfolio`, `review_decision`), либо смешением ответственностей (`candle_stats`,
   `ask`, `load_settings`). Независимые инструменты (radon, lizard, pyscn, pylint) указали на одни и
   те же методы. pylint W0212 нашёл скрытую связь через закрытое поле, которую CBO не учитывает.
3. После оптимизации нет ни одного нарушения правил сложности: максимальная CC снизилась с 30 до 7,
   все функции получили ранг A или B, максимальная когнитивная сложность — с 38 до 7, объём
   Холстеда модуля `market` уменьшился в 3,5 раза, покрытие выросло до 97 %.
4. **Суммарная сложность почти не изменилась (244 → 242), средний MI модулей тоже (48,3 → 48,2).**
   Декомпозиция не убирает существенную сложность задачи, а распределяет её по небольшим функциям,
   каждую из которых проще понять и протестировать. Реальное снижение есть только там, где устранено
   дублирование: у `market` MI вырос с 35 до 44.
5. У инструментов есть ограничения, которые нужно учитывать:
   * radon считает MI для модуля целиком, а не для каждого метода, как VS. Поэтому разбиение длинного
     метода на несколько функций почти не меняет MI модуля, а у модулей, которые стали длиннее
     (`mcp_client`, `llm`, `__main__`, `models`), он даже снизился. Формула radon учитывает и долю
     комментариев, так что MI можно «улучшить» комментариями, не меняя код;
   * разные инструменты по-разному определяют CC (учитывать ли `and`/`or`): у одного метода radon
     даёт 30, а mccabe — 8. Значения разных инструментов нельзя сравнивать напрямую, и порог правила
     нужно подбирать под конкретный инструмент;
   * LOC выросло на 48 строк из-за докстрингов и заголовков новых функций, хотя логических строк
     (LLOC) стало меньше. Для оценки объёма лучше подходят LLOC и SLOC;
   * pylint считает глубину наследования без `object`, а VS — с ним.
6. Выделение логики из обработчиков и точки входа дало побочный эффект: код стал тестируемым,
   и тест сразу нашёл реальный дефект (повторное подключение `Router`). Метрики стоит использовать
   как сигнал, где нужны ревью и тесты, а не как самоцель.
